# Планирование: анализ, идентификация проблем и поиск решений

### Предположения и допущения
В постановке нет некоторых деталей, поэтому я сделаю ряд предположений на базе которых уже буду строить свое решение.

1. В постановке нет ни слова о мониторинге и логировании, которые сейчас есть по данной системе. Исходя из отсутствия каких либо данных о нагрузке и как отдельные сервисы с ней справляются в описании проблем, предполагаю, что мониторинг отсутствует. Также нет на схеме или описании ничего о наличии централизованной схемы логирования, поэтому предполагаю, что логирование делается в рамках виртуальнальных машин в файлы.
2. По каким-то причинам команда не может быстро контейнизировать бэковые сервисы, которые сейчас на EC2 и перевести их на kubernetis. 

### Анализ схемы и описания системы. Потенциальные проблемные места

*Потенциально проблемные места*
1. Отсутствие мониторинга
Это серьезно снижает возможность понимать, справляются ли отдельные сервисы с текущей нагрузкой и где у нас у системы есть "бутылочные горлышки".
2. Отсутствие масшабирование бэковых сервисов в зависимости от нагрузки
В описание сказано, что у нас поднято на 1 инстансу всех бэковых сервисов, которые есть в системе. Это серьезное упущение с точки зрения надежности и обеспечения хотя бы минимальной масштабируемости системы.
3. Отсуствие системы централизованного логирования
Это также серьезно ограничивает команду в анализе ошибок и проблем в системе: снижает эффективность и скорость.
4. Отсутствие возможности масштабировать БД сервисов, хотя бы по паттерну read-replica
Не дает возможности достаточно просто масштабировать БД по достаточно простому принципу master-slave
5. Длительные расчеты проводяться на том же сервисе, что и работа с интерфейсом MES системы
Две крупные функциональности аобсолютно разного нагрузочное профиля собраны в один сервис, что существенно затрудняет реализацию гибкого мастабирования этого сервиса после его перевода на kubernetis
6. Единая база данных для CRMAPI и InternetAPI сервисов
Также снижает возможности по масштабированию сервисов

### Инициативы для необходимые для устранения потенциально проблемных места

*Повышение наблюдаемости приложение и "тушение пожара"*
1. Внедрить мониторинг на базе Prometeus и Grafana по системным метрикам на бэковых серверах, серверах БД и очереди сообщений на базе RabbitMQ
2. Масштабирование сервисов бэка в рамках EC2 схемы на 2-3 инстанса с балансировщиком на работающим по принципу sticky sessions (на мой взгляд наиболее безопасный способ для данных условий, хотя и не обеспечивает равномерную нагрузки инстансов)
3. Масштабирование БД через репликацию master-master на 2 инстанса !!!!!(Поддерживает ли PostgresSQL такой подход)

*Последующие действия повышающие прозрачность системы и ее мастабируемости*
1. Настроить ценрализованный мониторинг с бэковых серверов на базе ELK стека, чтобы повысить скорость разбора проблем и надежность системы
2. Контейниризация бэковых сервисов MES API, Shop API, CRM API и настройка автоматического их масштабирования в зависимости от нагрузки
3. Вынесение функционал по расчету стоимости модели из MES API в отдельный микросервис, который будет получать задачи на расчет и отпрвлять результата через очередь сообщений
4. Разделение базы для Shop API, CRM API
