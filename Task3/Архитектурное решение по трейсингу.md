# Архитектурное решение по трейсингу

### Анализ системы
Основные проблемы, которые сейчас есть в системе - проблема с обработкой заказов.
Соответсвенно нужно прежде всего организовать трейсинг компонентов, участвующих в изменении статусов заказов. Это CRM API, Shop API и MES API.

### Мотивация
Внедрение трейсинга позволит:
- отслеживать весь жизненный путь заказа (ускорит работу службы поддерки и ответ на обращеня пользователей)
- быстро определять где возникла ошибка с заказом (ускорит разбор инцидентов и исправление дефектов)
- найти места и выявить причина медленной работы сервисов (позволит повысит производительность системы и снизить время отклика для пользователей)

### Предлагаемое решение
Трейсинг будем реализовывать с помощью OpenTelemetry и Jaeger
![Диаграмма С4 после внедрения трейсинга](jewerly_c4_model.drawio)

### Компромиссы
Трейсинг может быть не применим или его внедрение стоить очень дорого:
- Использование проприетарного компонента, который будет очень сложно доработать так, чтобы он отдавал метрики
- Используется гибридное облако и нет возможности собирать метрики в одном месте из-за ограничений безопасности
- Нет возможности установить необходимые для организации трейсинга компоненты (нет ресурсов или запрет на установки необходимых компонентов от ИБ)

### Безопасность
Доступ на ПРОД будет предоставлен только сотрудникам поддержки и DevOps инженеру. 
На dev и release средах доступ будет предоставлен также всей команде разработки.
