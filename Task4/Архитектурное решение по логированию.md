# Архитектурное решение по логированию

### Анализ
Покрыть логированием в нашем случае нужно бэковые сервисы:
- Shop API
- СRM API
- MES API
Нам нужны логи приложения для возможности восстановить последовательность обработки и найти возможные дефекты.
Етественно, для ПРОД среды должны быть включены уровни логирования:
- FATAL
- ERROR
- WARN
- INFO

На уровне INFO залогируем:
- Все запросы и ответы бэковых микросервисов с указанием покупателя/менеджера/вызывающей внешней системы(API user), номера заказа (если возможно) и свозного индентификатора запроса (чтоб можно было посмотреть цепочку вызовов для обработки запроса пользователя)
- Все сообщения которые были записаны или считаны из очереди сообщений с указанием номера заказа
- Запросы на чтение и запись в S3 хранилище

### Мотивация
Внедрение логирования поможет:
- Быстро опредилить причину возникновелия сбоя\инцидента и операвно его устранить
- Достаточно просто оценить нагрузку на систему и выявить ее слабые места
- Дает возможность бизнесу оценить посещаемость и используемые сервисы
- Помогает специалистам по информационной безопасности выявить факты сесанкционированных действий и связанных с этим лиц

### Предлагаемое решение
Для реализации логирования предлагаю использовать стандартное решение - ELK стек. 
![Диаграмма С4 после внедрения трейсинга](jewerly_c4_model.drawio)

##### Безопасность
К логам ПРОДа доступ будет ограничен и предоставлен только сопровождению и тимлиду.
Для предотвращения логирования чувствительных данных будет разработано руководство сотрудниками ИБ, которое определит правила маскирования таких данных. (Например для банковских счетов принята схема 6 первых цифр и 4 последних, остальное заменяется звездочками)

##### Политика хранения логов
В ELK стеке будем хранить 14 последних дней логирования, более старые данные очищаем раз в день. 
Исходные файлы логов с бэковых серверов храним 3 месяца (для разбора в случае каких-то спорных ситуаций)

##### Превращения системы сбора логов в систему анализа логов
Для алертинга и поиска анамолий все же предлагаю использовать систему мониторинга вместо логирования. В том числе из-за этого я предлагаю систему мониторинга настроить ранее системы логирования.
Но в полне допускаю, что логи будут востребованы как основа для бизнес анализа системы со стороны продакт-менеджера системы и SEO-специалиста.
В этом случае лучше будет построить дополнителные индексы в elasticsearch и расшить время хранения логов в ELK хотя бы до 3х месяцев.
