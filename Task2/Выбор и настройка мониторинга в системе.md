# Выбор и настройка мониторинга в системе

### Мотивация
Внедрение системы мониторинга позволит:
- Намного быстрее выявлять и решать возникающие технические проблемы и сбои за счет получения оперативной информации о работе системы.
- Повысит надежности системы, что приведет к росту удовлетворенности пользователей за счет возможность быстрее находить источник проблемы и его устранять.
- Даст возможность повысить быстродействия системы и эффективности распределения ресурсов за счет выявления узких мест. 
- Повышение безопасности системы за счет получения оперативной полной информации о работе системы.


### Выбор подхода к мониторингу

1. Как подход к мониторингу бэковых серевисов я бы выбрал RED + Utilization
RED выбран, потому что наша система управляется запросами и нам важна скорость работы и минимум ошибок.
Утилизация добавлена, чтобы лучше проще было выбрать необходимую конфигурацию ресурсов для бэковых сервисов, т.к. сейчас выглядит так, что конфигурации не сбалансированы.

2. Для мониторинга БД и хранилища S3 и очереди сообщений на базе RebbitMQ больше подходит, на мой взгляд, USE.
В данному случае USE наиболее подходит для контроля этих сервисов.

### Выбранные метрики из возможных

##### Метрика для очереди сообщений
- Number of dead-letter-exchange letters in RabbitMQ
- Number of message in flight in RabbitMQ
Приведенные метрики - базовы для отслеживания количества необработанных сообщений (ошибок) и объема необработанной работы (насыщщености)

##### Метрики для бэковых сервисов
**Метрики метода RED**
- Number of requests (RPS) for internet shop API
- Number of requests (RPS) for CRM API
- Number of requests (RPS) for MES API
- **Number of HTTP 4xx for shop API**
- **Number of HTTP 4xx for CRM API**
- **Number of HTTP 4xx for MES API**
- Number of HTTP 500 for shop API
- Number of HTTP 500 for CRM API
- Number of HTTP 500 for MES API
- Response time (latency) for shop API
- Response time (latency) for CRM API
- Response time (latency) for MES API
Приведенные выше метрики как раз и позволят нам реализовать метод мониторинга RED

** Метрики позволяющие оценить утилизацию осноновных ресурсов: процессор и память**
- CPU % for shop API
- CPU % for CRM API
- CPU % for MES API
- Memory Utilisation for shop API
- Memory Utilisation for CRM API
- Memory Utilisation for MES API

##### Метрики для баз данных м S3 хранища
- Memory Utilisation for shop db instance
- Memory Utilisation for MES db instance
- Number of connections(idle, idle in transaction, active) for shop db instance
- Number of connections(idle, idle in transaction, active) for MES db instance
- **Max idle time in transaction for shop db instance**
- **Max idle time in transaction for MES db instance**
- **Max lock time in transaction for shop db instance**
- **Max lock time in transaction for MES db instance**
- **Number of errors for shop db instance**
- **Number of errors for MES db instance**
- Size of S3 storage
- **Number of requests (get, post) for S3 storage**
- **Bytes uploaded for S3 storage**
- **Bytes downloaded for S3 storage**
- **Total errors of S3 storage**

### План действия по внедрению мониторинга
1. Определить набор показателей, которые будут отслеживаться
2. Развернуть и настроить Prometeus
3. Развернуть агенты сбора метрик для prometeus на виртуальных машинах, где стоят бэковые сервисы
4. Развернуть агенты для сбора метрик от PostgreeSQL, RabbitMQ и S3 хранилища
5. Настроить подключение Prometeus к агентам
6. Развернуть Grafana, настроить подключение к Prometeus
7. Настроить в grafana дашборды для отслеживания метрик
8. Настроить в grafana alert'ы, чтобы можно было оперативно реагировать на сбои
